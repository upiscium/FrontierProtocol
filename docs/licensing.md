# Licensing and Provenance

## Scope and conclusion

Frontier Protocol's project-authored source code, tests, data definitions,
documentation, and original artwork are licensed under the top-level
[BSD 3-Clause License](../LICENSE). Repository history identifies the project
author as the author of these materials, and the source audit found no foreign
Java package implementation or copied dependency source in active or legacy
project code.

BSD-3-Clause applies only to Frontier Protocol material. It does not relicense
Minecraft, NeoForge, Create, Create: The Factory Must Grow (TFMG), Fungal
Infection: Spore, Gradle, KubeJS, JEI, Ponder, Flywheel, or any other dependency.
Names, package names, registry identifiers, method descriptors, and API calls
identify interoperability targets and remain subject to their owners' rights.

## Frontier Protocol material

- **Production Java source:** implementation under
  `src/main/java/dev/upiscium/frontierprotocol/` is authored for this project.
  Any residual NeoForge MDK bootstrap structure is permitted by and retains the
  repository's `TEMPLATE_LICENSE.txt`; Frontier Protocol-specific modifications
  are BSD-3-Clause. Imports of Minecraft, NeoForge, Create, TFMG, and Spore APIs
  are links to external interfaces, not copies of their source.
- **Unit tests and GameTests:** `src/test/java/` and Frontier Protocol GameTest
  classes under `src/main/java/` are project-authored verification code. Their
  assertions use public APIs and dependency identifiers.
- **External APIs and Mixins:** Frontier Protocol's Mixin classes and
  configuration are project-authored integration code. Target class names,
  descriptors, call-site counts, registry identifiers, and imports describe
  compatibility with external APIs; no target implementation source is copied.
- **Generated resources:** committed files under `src/generated/resources/`
  are deterministic outputs of Frontier Protocol's datagen providers. Minecraft,
  NeoForge, Create, and TFMG serializer, tag, item, block, and fluid identifiers
  remain identifiers owned or defined by those projects.
- **JSON resources:** Frontier Protocol blockstates, models, tags, language
  files, Mixin configuration, and data definitions are project-authored. Model
  parents such as `minecraft:item/generated` and direct Create casing resource
  references do not copy the referenced model or texture.
- **Compound and Cell artwork:** the two 32x32 RGBA item textures and their
  model definitions were created for Frontier Protocol in R10. No Minecraft,
  Create, TFMG, or Spore texture is embedded in those images.
- **Stabilizer models and textures:** the shared model, blockstates, item
  models, and 18 Tier 1/2/3 face textures were created for Frontier Protocol in
  R11. They use Create's casing-machine visual language, but no Create PNG is
  copied or modified. Bottom faces resolve Create casing textures at runtime.
- **Documentation and Ponder content:** repository documentation, localized
  text, Ponder scene code, and the three committed Ponder schematics are
  project-authored. Scenes refer to dependency blocks and items without
  redistributing dependency assets.
- **Other repository material:** project-specific CI, Nix, Gradle additions,
  configuration, plans, and examples are Frontier Protocol material except for
  the third-party items identified below.

## Legacy reference source

`src/reference/` preserves the project's R0 implementation and related tests.
Its history attributes it to the same project author, so it is covered by the
repository BSD-3-Clause license. It is intentionally outside every Gradle source
set, is neither compiled nor packaged, and does not become active compatibility
code. Public source distributions include it only as historical project source.

## Generated and binary fixtures

- `empty.nbt` is generated by Frontier Protocol's Gradle build.
- `r9_physical_mechanical_crafting.nbt` and the committed Ponder NBT files were
  created for Frontier Protocol's tests and scenes.
- `r9_unheated_mixing.nbt` is copied at build time from Create 6.0.11's
  `data/create/structure/gametest/processing/brass_mixing.nbt`. Create classifies
  non-asset files under its MIT terms. The complete upstream notice is retained
  in `src/main/resources/META-INF/LICENSES/Create-LICENSE.md` and packaged in the
  production JAR. This fixture is not claimed as BSD-3-Clause project artwork.
- Generated `META-INF/neoforge.mods.toml` retains NeoForge MDK-derived template
  structure and combines it with Frontier Protocol metadata. The repository
  `TEMPLATE_LICENSE.txt` remains the sole authoritative MIT notice. The JAR task
  packages a byte-identical copy as
  `META-INF/LICENSES/NeoForge-MDK-TEMPLATE-LICENSE.txt`.

## Retained third-party material

- NeoForge MDK template files retain the MIT notice in `TEMPLATE_LICENSE.txt`.
  Later Frontier Protocol-specific modifications are covered by BSD-3-Clause
  without removing the upstream notice. The packaged byte-identical notice
  applies only to retained NeoForge MDK template material; it does not license
  the whole project or JAR under MIT.
- `gradle/wrapper/gradle-wrapper.jar` is the Gradle wrapper and contains its own
  embedded Apache License 2.0 text. It is repository tooling and is not packaged
  in the production mod JAR or release candidate.
- The Create notice packaged under `META-INF/LICENSES/` applies to the audited
  Create GameTest fixture described above. Its restrictive asset terms are also
  preserved verbatim even though no Create asset-directory file is copied.

## Distribution boundary

The production JAR contains Frontier Protocol classes and resources, the
authoritative project `LICENSE`, the retained Create fixture notice, and the
byte-identical NeoForge MDK template notice. It does not shade Minecraft,
NeoForge, Create, TFMG, Spore, or other dependency classes.
The release candidate contains exactly the Frontier Protocol JAR, its SHA-256,
the release manifest, and the standalone project `LICENSE`; dependency JARs and
dependency assets are not bundled. Users must obtain dependencies separately
under each dependency's own terms.
