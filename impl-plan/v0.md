# Frontier Protocol — Codex向け設計・実装仕様書

- 文書状態: Draft 0.2
- 対象: Minecraft Java Edition 1.21.1 / NeoForge 21.1.x / Java 21
- 正式MOD名: Frontier Protocol
- 正式MOD ID: `frontier_protocol`
- 正式Javaパッケージ: `dev.upiscium.frontierprotocol`
- リポジトリ名: `frontier-protocol`
- 必須依存: NeoForge，Create
- 任意依存: KubeJS，TFMG，Create Aeronautics / Simulated，FTB Quests

> この文書はCodexが実装判断に使用する一次仕様である．ここにない機能を推測で追加しないこと．疑義がある場合は，最小実装・疎結合・サーバー権威を優先すること．

## 1. Codexへの実行指示

1. 最初にリポジトリ全体，`build.gradle`，`gradle.properties`，NeoForge/ Createのバージョンを確認する．
2. Minecraft 1.21.1，NeoForge 21.1.x，Java 21を固定する．別バージョンへ勝手に更新しない．
3. 各マイルストーンを個別PR相当の小さな変更として実装する．一度に全機能を作らない．
4. 実装前に対象マイルストーンのテストを追加する．少なくとも純粋ロジックの単体テストかGameTestのどちらかを用意する．
5. CreateのContraption，Aeronautics/Simulatedの物理船，TFMG内部クラスには直接依存しない．
6. Mixin，reflection，access transformerで他MOD内部へ侵入しない．
7. 他MODとの連携は，レシピ，タグ，通常のアイテム・流体Capability，データパック，任意依存判定に限定する．
8. Createとの固定設備連携は許可する．ただしContraption上での独自挙動は実装しない．
9. クライアントから送信された状態を信用しない．ゲーム進行，保護，感染，食事履歴はすべてサーバー側で判定する．
10. API名が本書と現行NeoForgeマッピングで異なる場合は，1.21.1の公式MDK・ソース・JavaDocを確認して同等APIを使用する．
11. `TODO`だけの未実装，空のイベントハンドラー，例外を握り潰す処理を残さない．
12. 任意依存MODが存在しない構成でも起動・ワールド生成・テストが成功すること．

## 2. プロダクトビジョン

Frontier Protocolは，Create中心の工業MODPackに次のゲームループを提供する薄い専用MODである．

1. 初期安全区で基礎工場を作る．
2. 世界を探索し，希少な"特性セクター"を発見する．
3. 特性セクターを保護し，その領域固有の資源生産設備を稼働させる．
4. Createの鉄道・物流で複数領域の生産物を中央工場へ集約する．
5. 保護装置へ消耗品を継続供給し，安全圏を維持する．
6. 初期地点から遠いほど強化されたバニラMobと，放置により成長する感染巣へ対処する．
7. 食料の多様性を維持し，農業・食品自動化にも継続的な需要を作る．

世界の大部分は無特性の通常セクターであり，建築，鉄道，倉庫，居住区，一般農業に自由に利用できる．特性セクターだけが希少な恒久生産源として価値を持つ．

## 3. 明確な非目標

以下は実装しない．

- 新規Mob，独自Entity，独自アニメーション
- ブロックが感染ブロックへ置換される地形侵食
- 未ロードチャンクでの感染進行
- 世界全体を毎Tick走査する感染シミュレーション
- Aeronautics/Simulatedの船体，座標系，物理演算への直接統合
- 船に追従する移動式保護領域
- Mobが物理Contraptionを認識，搭乗，追跡，破壊するAI
- 資源ノードや保護塔をContraption上で稼働させる機能
- TFMG内部の油田，機械，レシピ実装への直接フック
- FTB Questsをワールド状態の正規保存先として使用すること
- 全セクターへの特性付与
- 特性セクター内でしか通常クラフトや通常Create加工ができない制限
- 保護燃料が切れた瞬間に拠点を破壊する即時ペナルティ
- 船体ブロック数を独自Mixinで制限する機能

Aeronauticsの船体上限は，Aeronautics/SimulatedまたはCreateが公開する標準設定・公開APIが存在する場合のみ外部設定で行う．公開手段がない場合，MVPでは実装しない．

## 6. ワールドデータモデル

### 6.1 FrontierProtocolWorldData

OverworldのSavedDataとして保存する．

```java
public final class FrontierProtocolWorldData extends SavedData {
    int schemaVersion;
    long worldSeedFingerprint;
    int originChunkX;
    int originChunkZ;
    int sectorSizeChunks;
    Map<SectorPos, ResourceLocation> forcedTraitOverrides;
    Set<SectorPos> discoveredSectors;
}
```

要件:

- 初回ワールドロード時に初期ワールドスポーンのチャンク座標を保存する．
- ベッド，Respawn Anchor，後日のプレイヤーリスポーン変更では原点を変更しない．
- `sectorSizeChunks`は初回生成時に保存し，以後Server Configを変更しても既存ワールドでは変えない．
- Configとの差異がある場合は警告ログを出し，保存済み値を優先する．
- `forcedTraitOverrides`には保証配置，管理コマンドによる設定だけを保存する．
- 全セクターの特性を保存してはならない．

MVPではOverworldのみを対象とする．NetherとEndではセクター特性，感染，距離強化，保護を無効にする．将来，Dimensionごとの設定を追加可能な構造にする．

### 6.2 SectorPos

```java
public record SectorPos(int x, int z) {
    public static SectorPos fromChunk(ChunkPos chunk, int sectorSize) {
        return new SectorPos(
            Math.floorDiv(chunk.x, sectorSize),
            Math.floorDiv(chunk.z, sectorSize)
        );
    }
}
```

負座標でも必ず`Math.floorDiv`を使う．通常の整数除算は禁止する．

距離はチェビシェフ距離を標準とする．

```java
int distance = Math.max(
    Math.abs(sector.x() - originSector.x()),
    Math.abs(sector.z() - originSector.z())
);
```

### 6.3 ChunkInfectionState

ChunkへのData Attachmentとして保存する．

```java
public final class ChunkInfectionState {
    int schemaVersion;
    float pressure;             // 0.0 - 100.0
    InfectionStage stage;
    Optional<BlockPos> corePos;
    Optional<BlockPos> nestPos;
    long activeLoadedTicks;
}
```

`InfectionStage`:

```text
DORMANT      pressure 0-19
PRESENT      pressure 20-39
ESTABLISHED  pressure 40-59
CORE         pressure 60-79
NEST         pressure 80-100
```

Stageは保存値を信用せず，ロード時または変更時にPressureから再計算できるようにする．

### 6.4 MobScalingState

EntityへのData Attachment．

```java
public final class MobScalingState {
    boolean applied;
    int distanceTier;
    boolean outbreakCarrier;
    Optional<UUID> sourceNestId;
}
```

能力補正を二重適用しないため，`applied`を必ず確認する．

### 6.5 NutritionState

PlayerへのData Attachment．

```java
public final class NutritionState {
    int schemaVersion;
    Deque<ResourceLocation> recentFoods;       // default max 8
    Deque<ResourceLocation> recentCategories;  // default max 8
}
```

死亡時も保持する．プレイヤー複製イベントで確実にコピーする．

## 7. セクター特性システム

### 7.1 原則

- 大部分のセクターは無特性である．
- 1セクターは最大1特性だけを持つ．
- 特性は決定論的に算出する．同じSeedと設定では同じ結果になる．
- 特性は単独のノイズ点ではなく，1〜複数セクターのまとまりを形成する．
- 希少特性ほど，アンカー間隔を広くし，出現確率を下げる．
- 進行必須特性にはスポーン周辺の保証配置を持たせる．
- 特性は一次生産源だけを制限する．通常クラフト，通常Create加工，建築を制限しない．

### 7.2 初期MVP特性

| ID | 概要 | レア度 | 最低距離 | 役割 |
|---|---|---:|---:|---|
| `frontier_protocol:ferrous_strata` | 鉄質層 | common | 2 sectors | 鉄系無限資源ノード |
| `frontier_protocol:fertile_basin` | 肥沃地 | common | 1 sector | 食料，繊維，バイオマス |
| `frontier_protocol:resonant_crust` | 結晶層 | rare | 6 sectors | 安定化セル主要素材 |
| `frontier_protocol:oil_field` | 原油地帯 | rare | 8 sectors | TFMG原油・石油産業 |
| `frontier_protocol:old_industrial_zone` | 旧工業地域 | very_rare | 10 sectors | 設計図，スクラップ，技術解禁 |

MVPの最初の実装対象は`ferrous_strata`，`fertile_basin`，`resonant_crust`の3種類とする．原油地帯はResource Node API完成後に追加する．

### 7.3 JSON定義

配置ファイル:

```text
data/frontier_protocol/frontier_protocol/sector_traits/<name>.json
```

例:

```json
{
  "priority": 100,
  "placement": {
    "spacing": 10,
    "separation": 4,
    "anchor_chance": 0.35,
    "min_distance": 6,
    "max_distance": null,
    "cluster_min": 1,
    "cluster_max": 2,
    "salt": 918273
  },
  "guarantee": {
    "enabled": true,
    "count": 1,
    "ring_min": 6,
    "ring_max": 8
  },
  "resource_nodes": [
    "frontier_protocol:resonant_crystal_node"
  ]
}
```

全値をCodecで検証する．

検証要件:

- `spacing >= 1`
- `0 <= separation < spacing`
- `0.0 <= anchor_chance <= 1.0`
- `cluster_min >= 1`
- `cluster_max >= cluster_min`
- `min_distance >= 0`
- `ring_max >= ring_min`
- 重複IDはエラー
- 不正なResourceLocationはデータパックリロードを失敗させ，明確なログを出す

### 7.4 決定論的配置アルゴリズム

1. Traitごとに独立した配置グリッドを持つ．
2. 任意セクターを問い合わせると，その周辺の配置セルだけを調べる．
3. 各配置セルは`worldSeed + salt + cellX + cellZ`から1つのアンカー候補を決定する．
4. `anchor_chance`，最低距離，separationを判定する．
5. アンカーから決定論的なフットプリントを生成する．
6. 複数Traitが競合した場合，`priority`が高いものを採用する．同値ならResourceLocationの辞書順で決定する．
7. 強制Overrideが存在する場合は常にOverrideを優先する．
8. どのTraitにも該当しない場合は`Optional.empty()`を返す．

問い合わせはチャンク生成を要求してはならない．Biome条件はMVPでは実装しない．

計算結果はLRUキャッシュへ保存するが，正規データはSeedと定義であり，キャッシュを永続化しない．

### 7.5 保証配置

ワールド初期化時に，`guarantee.enabled`のTraitごとに指定リングを決定論的に走査する．

- 必要数の自然配置が存在すれば何もしない．
- 不足している場合はリング内の通常セクターを選び，`forcedTraitOverrides`へ追加する．
- Trait同士の保証配置が重ならないようにする．
- 原点5×5保護範囲と重なるSectorは避ける．
- 保証配置は一度だけ行い，データパック更新で勝手に再配置しない．

### 7.6 発見

MVPではプレイヤーが未発見セクターへ入った時点で世界共有の`discoveredSectors`へ追加する．

特殊Traitだった場合:

- ActionBarまたはChatで特性名を表示する．
- `SectorInfoPayload`をクライアントへ送る．
- `SectorDiscoveredEvent`を発火する．

通常セクターも発見済みとして保存する必要はない．特殊Traitを持つセクターだけ保存してよい．

## 8. 保護システム

### 8.1 初期永久保護

初期ワールドスポーンチャンクを中心に5×5チャンクを永久保護する．

判定:

```java
Math.abs(chunkX - originChunkX) <= 2
&& Math.abs(chunkZ - originChunkZ) <= 2
```

この保護はブロック，Block Entity，燃料を持たず，常に有効である．

### 8.2 Stabilization Beacon

MVPの固定式保護装置．

- 範囲: 設置チャンク中心3×3チャンク
- Block Entityを持つ
- 燃料Inventory 1 slot
- 内部燃料時間を保持
- Redstone無効化をサポート
- 自身のチャンクがロードされている時だけ稼働・燃料消費する
- Contraption搭載時の稼働は保証しない
- データパックタグでCreateの非移動対象へ登録する

状態:

```text
ACTIVE   fuelTicks > 0 and enabled
GRACE    fuelTicks == 0 and graceTicksRemaining > 0
OFFLINE  fuelTicks == 0 and grace expired
```

挙動:

| 状態 | 感染上昇 | 巣成長/スポーン | Mobブロック破壊 |
|---|---|---|---|
| ACTIVE | 停止 | 停止 | 禁止 |
| GRACE | 停止 | 停止 | 禁止 |
| OFFLINE | 再開 | 再開 | 許可 |

GRACEのデフォルトは6000 ticks(5分)．Server Configで変更可能．

### 8.3 燃料定義

燃料はItem RegistryへのData Mapで定義する．

概念:

```json
{
  "values": {
    "kubejs:stabilization_cell": {
      "ticks": 36000
    },
    "kubejs:industrial_stabilization_cell": {
      "ticks": 144000
    }
  }
}
```

Core MODはKubeJSのクラスへ依存しない．存在しないItem IDはデータロード時に明確に無視またはエラー報告する．

### 8.4 ProtectionService

公開インターフェース:

```java
public interface ProtectionService {
    boolean isChunkProtected(ServerLevel level, ChunkPos chunkPos);
    boolean isBlockProtected(ServerLevel level, BlockPos blockPos);
    Optional<ProtectionSource> findSource(ServerLevel level, ChunkPos chunkPos);
}
```

要件:

- 毎回全Block Entityを検索しない．
- ロード済みBeaconをChunk座標で空間Indexへ登録する．
- Block Entity load/unload/removeでIndexを更新する．
- 1チャンクに複数保護源が重なっても問題なく動作する．
- 初期永久保護を最初に判定する．
- Protection判定はServer Thread上で実行する．

### 8.5 保護対象

保護中に停止・拒否するもの:

- チャンク感染Pressureの増加
- 感染核の生成
- 感染核の成熟
- 巣によるMob生成
- Frontier ProtocolのBreachGoalによるブロック破壊
- hostile Mobを発生源とする爆発のブロック破壊

既存Mob，感染核，巣を自動削除しない．保護は問題を消すのではなく進行を停止する．

## 9. 距離によるMob強化

### 9.1 対象

デフォルト対象:

- Zombie系
- Skeleton系
- Spider系
- Creeper
- Witch
- Pillager系

Entity Type Tagで管理する．

```text
#frontier_protocol:distance_scaled_mobs
#frontier_protocol:outbreak_carriers
#frontier_protocol:breacher_mobs
```

### 9.2 適用タイミング

- Mobのスポーン完了時に1回だけ適用する．
- Natural，Chunk Generation，Spawner，Frontier Protocol Nest由来を対象にできるようConfig化する．
- Command，Structure，他MOD召喚はデフォルトでは除外する．
- `MobScalingState.applied`がtrueなら再適用しない．

### 9.3 Tier

初期値:

| Tier | 原点からのチャンク距離 | Health | Attack | Armor | Speed |
|---|---:|---:|---:|---:|---:|
| 0 | 0-15 | 1.00 | 1.00 | +0 | 1.00 |
| 1 | 16-39 | 1.25 | 1.15 | +1 | 1.02 |
| 2 | 40-79 | 1.60 | 1.35 | +3 | 1.05 |
| 3 | 80-127 | 2.10 | 1.60 | +5 | 1.08 |
| 4 | 128+ | 2.70 | 1.90 | +8 | 1.12 |

実際の値はServer Configまたはデータ定義へ移す．

距離は原点Chunkからのチェビシェフ距離で計算する．

属性Modifierは重複しない安定IDを使用する．適用直後に新規MobのHealthを新しいMax Healthへ合わせる．

### 9.4 データ駆動

Entity TypeへのData Mapで，Mobごとの補正許可，上限，装備率などを定義可能にする．

MVPでは共通Tier倍率だけでもよいが，JavaコードへEntity IDごとのif文を増やさない．

## 10. 感染・巣システム

### 10.1 感染の定義

感染はブロック置換ではなく，ロード中Chunkに保存されるPressureと巣の状態で表現する．

### 10.2 Outbreak Carrier

対象Mobが自然スポーンした時，保護外であれば`outbreakCarrier=true`を付与する．

初期MVPでは対象Tag内のMobをすべてCarrierとしてよい．

Carrierは以下の条件でPressureへ寄与する．

- 対象Chunkがロード中
- 保護外
- 128 blocks以内にServerPlayerが存在
- Mobが生存中
- Chunkが処理Budget対象

Carrier 1体につき，Slow Tickごとに設定値だけPressureを増やす．

プレイヤーがCarrierを倒した場合，死亡地点ChunkのPressureを少量減らす．0未満にしない．

### 10.3 Slow Tick

感染処理は毎Tick行わない．

- 基本間隔: 100 ticks(5秒)
- Server Levelごとにロード済み対象ChunkをBudget付きで処理
- 1回の処理上限をConfig化
- プレイヤー周辺Chunkだけを候補にする
- 全Entity，全Chunkを毎回検索しない
- Active CarrierとNestをIndex化する

### 10.4 感染核

Pressureが`coreThreshold`を超え，Coreが存在しない場合に生成候補を探す．

生成条件:

- 保護外
- プレイヤーが近すぎない．デフォルト24 blocks以上
- Bed，Respawn Anchor，Protection Beaconから16 blocks以上
- Block Entityから8 blocks以上
- 地面Blockが`#frontier_protocol:infection_core_ground`に含まれる
- 置換先が空気または`#frontier_protocol:infection_core_replaceable`
- Chunk内にCore/Nestが存在しない

位置探索は候補数を制限し，Chunk全体を総当たりしない．

### 10.5 成熟

Coreはロード中かつ保護外の時だけ`activeLoadedTicks`を増加させる．

- デフォルト成熟時間: 24000 ticks(20分)
- 保護中は完全停止
- Core破壊でPressureを大きく減らす
- 成熟時に同位置をInfection Nestへ置換する

### 10.6 Infection Nest

- Block Entityを持つ
- 独自Mobは生成しない
- Vanilla Mobを生成し，CarrierとsourceNestを付与する
- 生成Mob種はTag/Data定義で決定する
- Local CapとGlobal Capを持つ
- 保護中は生成しない
- プレイヤーが一定距離以内にいる場合のみ生成する
- 1Chunk 1 Nestまで

初期値:

```text
spawn interval: 600-1200 ticks
local cap: 12
radius: 24 blocks
global Frontier Protocol nest mob cap: 80
```

### 10.7 伝播

隣接ChunkへのPressure伝播はMVPに含めない．MVPが安定した後，低頻度・上限付きで追加を検討する．

## 11. Mobのブロック破壊AI

### 11.1 対象

`#frontier_protocol:breacher_mobs`に含まれるMobだけへBreachGoalを追加する．初期値はZombie，Husk．

### 11.2 破壊条件

すべて満たす場合のみ破壊する．

- `mobGriefing` Gameruleがtrue
- MobがPlayerをTargetとしている
- 通常Pathが一定時間成立していない
- 対象Blockが`#frontier_protocol:mob_breakable`に含まれる
- 対象BlockがBlock Entityではない
- HardnessがServer Config上限以下
- 対象Block位置が保護外
- Mobから短距離．デフォルト2 blocks以内

破壊対象は明示Allowlistで管理する．Blacklist方式は禁止する．

初期Allowlist候補:

- 木のDoor，Trapdoor，Fence，Planks
- Glass系
- Wool系
- Dirt，Cobblestoneなど低Tier防壁

Create，TFMG，Aeronautics，Container，Rail，Machineはデフォルトで含めない．

### 11.3 破壊処理

- 破壊時間はHardnessから算出し，Configで倍率を調整する．
- Server側でBlock Break Progressを送る．
- Target変更，Protection開始，距離超過で中止する．
- Dropはデフォルト無効．Configで変更可能．
- 1Mobが同時に複数Blockを処理しない．
- 毎Tick広範囲探索しない．前方とPath障害周辺の少数候補だけを見る．

### 11.4 Contraption

物理Contraption，Create Contraption，Aeronautics船を認識・破壊する処理は実装しない．

## 12. 食事多様性システム

### 12.1 目的

同じ食料だけを大量生産する最適解を弱め，複数食材・料理ラインへ需要を作る．

### 12.2 対象

- ServerPlayerがFoodPropertiesを持つItemを食べ切った時
- CakeのようなBlock食料はMVPでは対象外でもよい
- Milk，PotionなどFoodPropertiesを持たない飲料は対象外

### 12.3 カテゴリ

Item Tagで定義する．

```text
#frontier_protocol:food_categories/grain
#frontier_protocol:food_categories/vegetable
#frontier_protocol:food_categories/fruit
#frontier_protocol:food_categories/meat
#frontier_protocol:food_categories/fish
#frontier_protocol:food_categories/dairy
#frontier_protocol:food_categories/soup
#frontier_protocol:food_categories/dessert
#frontier_protocol:food_categories/preserved
```

1アイテムが複数カテゴリに属する場合，優先順位表か全カテゴリ記録のどちらかを決める．MVPではResourceLocation辞書順で最初の1カテゴリを採用し，ログ警告を出す．

### 12.4 効率計算

直近8食における，今回食べるItemの過去出現回数を数える．

| 過去回数 | 基本効率 |
|---:|---:|
| 0 | 1.00 |
| 1 | 0.85 |
| 2 | 0.65 |
| 3 | 0.45 |
| 4+ | 0.25 |

同カテゴリが直近8食中6回以上なら，カテゴリ係数0.80を掛ける．

```text
finalEfficiency = max(0.25, itemEfficiency * categoryEfficiency)
```

### 12.5 適用方法

Vanillaが食料値を適用した後，食事前後のFood LevelとSaturation差分を取得し，効率を超える分を差し引く．

実装は以下を保証すること．

- Food Levelを食事前未満へ下げない
- Saturationを0未満へしない
- Creativeでも履歴記録するかはConfig化
- Client表示だけで判定しない
- 食事完了後に今回のItem/CategoryをQueueへ追加する

### 12.6 フィードバック

MVPでは食後にActionBar表示する．

```text
栄養効率: 65% — 同じ食料が続いている
```

Clientへ完全な食事履歴を同期する必要はない．計算結果だけPayloadで送る．

## 13. 固定式資源ノード

### 13.1 原則

- 資源ノードは特性セクター内だけで稼働する．
- ノードBlock自体は移動不可．
- 一次生産のみ領域制限を受ける．
- 生成物の加工はどこでも可能．
- 完全枯渇させず，継続的な物流網に価値を残す．
- 稼働には保護状態を要求できる．

### 13.2 ResourceNodeDefinition

```json
{
  "required_trait": "frontier_protocol:ferrous_strata",
  "requires_protection": true,
  "work_interval": 200,
  "output": {
    "item": "kubejs:mixed_ferrous_ore",
    "count": 1
  }
}
```

定義はData Pack Reload可能にする．

### 13.3 Resource Node Block Entity

MVP仕様:

- 1 output inventory
- 固定周期でItemを生成
- 必要Traitでない場合停止
- 保護が必要な定義なら，保護外で停止
- 出力満杯なら停止
- Contraption化を拒否するData Tagを付与
- GUIは最小限．状態，Trait，停止理由を表示

### 13.4 Create連携

Createは必須依存として，将来的に固定式Node Controllerへ回転力要求を追加してよい．

ただし初期Resource Node APIでは，処理判定をインターフェースへ分離する．

```java
public interface WorkRequirement {
    WorkResult evaluate(ServerLevel level, BlockPos pos);
}
```

Create回転力要求は`CreateCompat`側で実装し，Sector/ProtectionロジックへCreateクラスを漏らさない．

### 13.5 原油地帯とTFMG

原油地帯は次の段階で実装する．

- `frontier_protocol:oil_field` Trait
- 固定式Oil Well Controller
- TFMGが存在する場合，設定された原油Fluidを通常Fluid Capabilityへ出力
- TFMGが存在しない場合は稼働不可と表示し，クラッシュしない
- TFMG内部油田クラスや内部Recipeクラスを参照しない
- 出力Fluid IDはJSON/Configで定義し，ハードコードしない

製油，ディーゼル，ガソリン，LPG，鋼材などの加工はTFMG本体とKubeJSレシピへ任せる．

## 14. Aeronautics / Simulated連携方針

Core MODはAeronautics/Simulatedへのコンパイル依存を持たない．

許可する連携:

- 航空部品用の追加素材とレシピ
- TFMG鋼材，燃料，潤滑油を使うKubeJSレシピ
- 地上固定の航空整備・補給ブロック
- セクター調査結果を扱う固定式解析装置
- 通常ワールド上のPhantom，Skeleton，Pillager等の挙動調整
- Aeronautics/Simulatedの公開Server ConfigをMODPack側で設定

禁止する連携:

- 船上で動く保護装置
- 移動式資源ノード
- 船体への力，揚力，推進力追加
- 船体座標変換
- Mobの船体認識，乗船，船体破壊
- 独自Block Entityの船上Tick保証
- Mixinsでの組立上限変更

独自BlockはCreateの非移動Tagへ登録する．正確なTag IDは採用Createバージョンのデータを確認して決める．

船体ブロック数上限はCore MODの責務外とする．公開設定がある場合のみMODPack設定として扱う．

## 24. 最終設計原則

1. **通常領域を無価値にしない．** 通常セクターは自由な建築・物流用地である．
2. **特殊領域は疎である．** 希少性によって探索と鉄道建設を生む．
3. **一次生産だけを領域依存にする．** 加工場所はプレイヤーが決める．
4. **保護は危険への投資報酬である．** 保護後も燃料物流を要求する．
5. **感染はロード中だけ進む．** 放置サーバーや未訪問地域を破壊しない．
6. **新規Mobを追加しない．** バニラMobへ役割と背景を与える．
7. **Allowlistで破壊を制御する．** 工場を無差別に壊さない．
8. **Contraption内部へ侵入しない．** 更新追従コストと不安定性を抑える．
9. **データ駆動を優先する．** Trait，Mob，Fuel，Nodeを再コンパイルなしで調整可能にする．
