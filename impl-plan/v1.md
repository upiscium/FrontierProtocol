# Frontier Protocol 最終設計・既存実装移行指示書

## 1. この指示書の目的

本指示書は，NeoForge 1.21.1向けMOD"Frontier Protocol"の設計方針を確定し，旧設計に基づいてM6付近まで進行している既存実装を，新設計へ安全に移行するためのものである．

既存コードを無条件に削除したり，プロジェクトを作り直したりしてはならない．

最初に現在のリポジトリと作業ツリーを詳細に確認し，既存実装を以下へ分類すること．

1. 新設計でもそのまま利用できるもの
2. 小規模な修正で再利用できるもの
3. 将来利用する可能性はあるが，現時点では無効化すべきもの
4. 新設計と明確に競合し，削除すべきもの
5. テストやドキュメントのみ更新すべきもの

実装済み機能を，設計変更を理由に一括削除してはならない．

---

# 2. MODの最終的な定義

Frontier Protocolは，**Fungal Infection: SporeとCreateを統合するアドオンMOD**である．

主目的は，Sporeが提供する感染環境を，Createによる工業生産，自動化，動力供給および物流によって継続的に制御できるようにすることである．

Frontier Protocol自身が，新しい感染生態系や独自の資源無限化システムを構築することは目的としない．

本MODは，次のゲーム体験を提供する．

> プレイヤーはCreateによる生産設備と物流網を構築し，継続的な資材および動力の供給によってSporeの感染拡大を抑制し，感染世界の中に持続可能な拠点，工場および前線を維持する．

---

# 3. 各MODの責務

## 3.1 Fungal Infection: Spore

Sporeに以下を委譲する．

* 感染Mob
* Mob AI
* 感染ブロック
* 感染植生
* 地表および地下の感染侵食
* 巣，Hivemind，感染構造
* 感染の成長および拡大
* 戦闘コンテンツ
* Spore標準のCDU
* Spore独自の感染素材および装備

Frontier Protocolは，これらを原則として再実装しない．

## 3.2 Create

Createに以下を委譲する．

* 回転力
* Stressシステム
* 機械加工
* 混合
* 圧縮
* 充填
* アイテム輸送
* 流体輸送
* 工場の自動化
* 長距離物流の基礎

## 3.3 他のCreateアドオン

以下はFrontier Protocolの責務外とする．

* 鉱石の無限生成
* 流体貯留層
* 無限油田
* 特殊鉱床
* 地域別資源ノード
* 資源探査

これらはCreate Ore Excavationなど，既存のCreateアドオンへ委譲する．

## 3.4 Frontier Protocol

Frontier Protocolは以下だけに集中する．

* Spore感染を抑制する独自の安定化装置
* 安定化装置の3段階Tier
* チャンク単位かつディメンション全高の感染抑制
* Createによる装置部品および消耗品の製造
* Create回転力を利用した継続運転
* 安定化装置への継続的な資材供給
* 初期スポーン周辺の恒久的な感染抑制
* SporeとCreateのレシピ，タグ，素材および進行の統合
* 安定化範囲と稼働状態の表示
* 設定，データ永続化およびサーバー同期
* Spore互換処理

# 4. 明確な非目標

Frontier Protocolでは，以下を実装しない．

* 独自感染Mob
* バニラMobの感染Mob化
* 独自の感染核
* 独自の感染巣
* 独自の感染圧シミュレーション
* 距離依存のMob能力強化
* 資源セクター
* セクター特性
* 独自無限資源ノード
* 独自油田
* Mobの侵入阻止
* Mobの自動排除
* Mobのターゲット解除
* プレイヤーへの攻撃無効化
* Mobによるブロック破壊の全面無効化
* 爆発の全面無効化
* 完全無敵の安全地帯
* Create Contraption内部への広範な直接介入

Mobの侵入および拠点防衛はプレイヤーの責任とする．

プレイヤーは壁，堀，照明，防御設備，入口，迎撃設備などを自分で構築する．

# 5. Spore標準CDUとの役割分担

## 5.1 Spore標準CDU

Spore標準のCDUは変更せず，Spore本来の用途に残す．

想定用途は以下．

* 重感染地域への一時的な進出
* 局所的な感染除去
* 戦闘支援
* 前線での短期作業
* 感染MobへのFrostbite付与
* 狭い範囲の一時的制圧

Frontier Protocolは，原則としてSpore標準CDUの範囲，Frostbite処理，Block Entityまたは内部ロジックを直接置換しない．

## 5.2 Frontier Protocolの安定化装置

Frontier Protocolでは，Spore標準CDUとは別の独自ブロックを実装する．

この装置は，一時的な戦闘支援ではなく，Create工業によって維持される恒常的な感染抑制インフラである．

主な特徴は以下．

* チャンク単位の効果範囲
* ディメンション最低高度から最高高度まで有効
* プレイヤーへFrostbiteを与えない
* Mobの侵入には干渉しない
* Create回転力を要求する
* 消耗品または処理用流体を継続的に消費する
* 動力または消耗品が切れた場合，一定の猶予後に停止する
* Spore感染の新規生成，成長および拡散を抑制する
* 既存感染の浄化は段階的に行う
* 既存の巣を自動破壊しない

# 6. 3段階の安定化装置

Tierの名称は暫定であり，実装時に翻訳可能なIDとして定義する．

## 6.1 Tier 1: Field Containment Unit

暫定ID:

```text
field_containment_unit
```

役割:

* 前線拠点
* 小規模採掘拠点
* 鉄道駅
* 一時的な橋頭堡
* 単一チャンクの保護

仕様:

* 効果範囲: 設置チャンク1つ
* 範囲形状: 1×1チャンク
* 高さ: ディメンション全高
* 初期建設費: 低
* Stress消費: 低
* 維持効率: 低
* 浄化速度: 低
* 設置および撤去が容易
* Create初期から中期で製造可能

## 6.2 Tier 2: Industrial Containment Array

暫定ID:

```text
industrial_containment_array
```

役割:

* 恒久工場
* 通常規模の居住拠点
* 物流ハブ
* 中規模工業地区

仕様:

* 効果範囲: 装置が存在するチャンクを中心とした3×3チャンク
* 高さ: ディメンション全高
* 初期建設費: 中
* Stress消費: 中
* 維持効率: Tier 1より高い
* 浄化速度: 中
* Create中期から後期の加工設備を要求
* 必要に応じてTFMG素材を使用してよい

## 6.3 Tier 3: Regional Stabilization Core

暫定ID:

```text
regional_stabilization_core
```

役割:

* 都市
* 大規模工業地帯
* 主要拠点
* 終盤の恒久的な広域制圧

仕様:

* 効果範囲: 装置が存在するチャンクを中心とした5×5チャンク
* 高さ: ディメンション全高
* 初期建設費: 非常に高い
* Stress消費: 高い
* 維持効率: 最も高い
* 浄化速度: 高
* Create後期設備を要求
* TFMGが導入されている場合は，重工業素材や石油化学素材を利用可能
* 単独ブロックとして実装してよいが，将来的なマルチブロック化を妨げない設計にする

# 7. Tier設計上の原則

Tier差を効果範囲だけにしてはならない．

最低でも次のパラメータをTierごとに外部定義または設定可能にする．

* 効果半径チャンク数
* Stress消費
* 最低回転速度
* 消耗品容量
* 消耗速度
* 停止猶予時間
* 浄化速度
* 1回あたりの浄化処理上限
* 設置可能条件
* Contraption移動可否
* 稼働音
* パーティクル頻度

装置実装を3種類の独立したコピーコードにしてはならない．

共通の抽象化，共通Block Entityまたは共通の設定レコードを利用する．

例:

```java
public record StabilizerTierDefinition(
    int chunkRadius,
    int minimumRpm,
    float stressImpact,
    int fuelCapacity,
    int fuelConsumptionInterval,
    int gracePeriodTicks,
    int cleanupBudgetPerCycle
) {}
```

実際のNeoForgeおよびCreate APIに合わせて型や構成は調整してよい．

# 8. 感染抑制の仕様

## 8.1 抑制するもの

安定化装置の稼働範囲では，可能な限り以下を抑制する．

* 感染ブロックの新規生成
* 感染ブロックの他ブロックへの拡散
* 感染植生の成長
* 地下侵食
* 感染構造の自然成長
* Hivemindまたは感染源の進行
* Sporeによる感染地形への変換
* 感染由来の固定要素の新規配置

Sporeの実装上，一括してすべてを停止できない場合は，各処理経路を特定して段階的に対応する．

## 8.2 抑制しないもの

以下には干渉しない．

* 範囲外から侵入するMob
* 範囲内に既に存在するMob
* Mobの移動
* Mobの攻撃
* Mobのターゲット選択
* Mobのブロック破壊
* 通常の爆発
* プレイヤーへの通常ダメージ
* Spore以外の環境変化
* プレイヤーが意図的に配置した通常ブロック

## 8.3 既存感染

安定化装置を設置した瞬間に，対象範囲全体の感染を即座に消去してはならない．

動作を以下の2種類へ分離する．

### 即時抑制

装置が稼働を開始した時点から，新しい感染生成および拡散を拒否する．

### 漸進的浄化

既に存在する感染ブロックおよび感染植生は，処理予算に従って徐々に除去または復元する．

既存の巣，Hivemind，ボス相当の構造を安定化装置だけで自動破壊してはならない．

必要に応じて以下だけを適用する．

* 成長停止
* 新規スポーン停止
* 再生停止
* 弱体化
* プレイヤーによる攻略を可能にする状態への固定

最終的な破壊はプレイヤーに要求する．

# 9. パフォーマンス要件

チャンク全高を一定間隔で全走査してはならない．

以下のような処理は禁止する．

```java
for (int x = minX; x <= maxX; x++) {
    for (int y = minBuildHeight; y < maxBuildHeight; y++) {
        for (int z = minZ; z <= maxZ; z++) {
            inspect(level.getBlockState(new BlockPos(x, y, z)));
        }
    }
}
```

抑制と浄化を分ける．

## 9.1 抑制判定

感染が生成または拡散しようとする位置に対して，チャンク単位のO(1)に近い問い合わせを行う．

概念API:

```java
public interface InfectionSuppressionService {
    boolean isSuppressed(ServerLevel level, BlockPos pos);

    boolean isSuppressed(ServerLevel level, ChunkPos chunkPos);

    SuppressionSource getSuppressionSource(
        ServerLevel level,
        ChunkPos chunkPos
    );
}
```

稼働中装置が覆うチャンクを，ディメンション単位の索引へ登録する．

問い合わせ時に全Block Entityを走査してはならない．

## 9.2 浄化処理

既存感染の浄化は，以下のいずれか，または組み合わせで行う．

* チャンクセクション単位の分割走査
* 1サイクル当たりの処理ブロック数制限
* 感染ブロック位置の追跡
* SporeのBlock Entity一覧の利用
* ブロック変更イベントから候補位置を記録
* ランダムサンプリング
* ロード済みチャンクだけを処理
* サーバーtick budgetの導入

装置数が増えても，処理量が無制限に増加しない設計にする．

## 9.3 アンロードチャンク

原則として，安定化装置はチャンクローダーとして動作しない．

* 装置チャンクがアンロードされている間は，燃料を消費しない
* アンロード中に対象チャンクの浄化を進めない
* Spore側がアンロード中に感染処理を進めない限り，抑制状態の時間シミュレーションは不要
* 再ロード時に状態を正しく復元する

将来，チャンクローダー連携を追加する場合は別機能とする．

# 10. 装置の運転条件

各安定化装置は，最低でも以下を要求する．

* Create回転力
* Tierごとの最低RPM
* TierごとのStress消費
* 消耗品
* 有効なBlock Entity状態
* Sporeがロード済みであること

## 10.1 状態遷移

最低限，次の状態を持つ．

```text
OFFLINE
STARTING
ACTIVE
GRACE_PERIOD
STARVED
OVERSTRESSED
JAMMED
```

必要に応じて名称は変更してよい．

### OFFLINE

動力も消耗品もなく，抑制効果なし．

### STARTING

起動準備中．

設置直後に即座に最大効果を出してもよいが，視覚演出と状態管理のため短い起動時間を設定してもよい．

### ACTIVE

正常稼働中．

抑制と漸進的浄化を行う．

### GRACE_PERIOD

動力または消耗品が停止した直後の残留安定状態．

新規感染抑制は維持してよいが，浄化は停止する．

5〜10分程度を初期案とするが，設定可能にする．

### STARVED

消耗品不足．

猶予時間終了後は抑制を解除する．

### OVERSTRESSED

CreateネットワークがOverstressedになっている，最低RPMに達していない，または回転していない状態．

### JAMMED

Spore側の特殊イベントや将来の故障要素を表現するための予約状態．

MVPでは未使用でもよいが，状態設計が拡張可能であること．

# 11. 消耗品および製造ライン

Spore標準CDU用のIce Canister統合は残してよい．

ただし，Frontier Protocol独自の安定化装置には，独自の工業用消耗品を利用する．

最初から多数の中間素材を追加してはならない．

MVP候補:

* `empty_pressure_canister`
* `sterile_filter`
* `purification_agent`
* `stabilization_medium`
* `stabilization_cell`

すべてを必須にする必要はない．

まず最小限の製造ラインを設計する．

推奨する基本構造:

```text
金属加工
↓
空の耐圧容器

冷却材または抑制剤の混合
↓
安定化媒体

フィルターまたは浄化剤の組み込み
↓
未密閉セル

充填・圧縮・密閉
↓
安定化セル
```

Create工程の例:

* Mechanical Press
* Mechanical Mixer
* Basin
* Spout
* Deploying
* Sequenced Assembly

必ずしもすべてを使う必要はない．

工数を増やすためだけの工程は追加しない．

## 11.1 バランス原則

* 最初の製造ライン構築はある程度重い
* 完成後は自動量産できる
* 手掘りの希少資源を大量消費させない
* 常時稼働に必要な量を現実的に自動供給できる
* 大規模拠点ほど物流と生産設備が必要になる
* 単なるクラフト連打にはしない
* 燃料単価より，生産設備，動力，物流および停止リスクを主要コストにする

## 11.2 Tier別燃料

MVPでは，全Tierで同じ安定化セルを使用してよい．

Tierごとの差は消費速度，容量および効率で表現する．

複数種類のセルを導入する場合も，安易にTierごとに完全別アイテムを追加しない．

必要性が実プレイで確認されるまで，単一燃料を優先する．

# 12. 初期スポーン保護

Frontier Protocolは，初期スポーン周辺を感染から保護する．

## 12.1 範囲

初期案として，ワールド生成時の初期スポーン地点を中心とした5×5チャンクとする．

範囲はサーバー設定で変更可能にする．

設定候補:

```text
spawnProtectionEnabled
spawnProtectionRadiusChunks
spawnProtectionDimension
```

半径2チャンクなら5×5になる．

## 12.2 保護内容

初期スポーン保護は，安定化装置と同じ感染抑制サービスを利用する．

保護するもの:

* 感染ブロックの新規生成
* 感染拡大
* 地下侵食
* 感染植生の成長
* 巣または感染源の自然生成
* Spore由来の感染地形変換

保護しないもの:

* 外から侵入するMob
* Mobの攻撃
* Mobのブロック破壊
* 爆発
* 通常Mobのスポーン
* プレイヤーの死亡
* 防壁なしでの安全

初期スポーン保護は，安全な建築用地を保証するものであり，無敵領域を保証するものではない．

## 12.3 永続化

ワールド作成後にベッドやコマンドでスポーン地点が移動しても，保護中心を自動移動させない．

最初に確定した保護中心をSavedDataへ保存する．

管理者向けコマンドにより再設定可能にしてよい．

候補:

```text
/frontierprotocol spawn-protection info
/frontierprotocol spawn-protection set
/frontierprotocol spawn-protection enable
/frontierprotocol spawn-protection disable
```

コマンドはMVP後でもよい．

# 13. Sporeとの統合方針

## 13.1 依存関係

SporeとCreateを必須依存とする構成を基本とする．

`neoforge.mods.toml`またはNeoForge 1.21.1の正しいメタデータ形式で，対応バージョンを明示する．

Sporeの内部APIやクラスへ直接依存する場合は，対応バージョンを狭く固定する．

## 13.2 統合優先順位

以下の順番で実装する．

1. NeoForge標準イベント
2. Sporeが提供する公開APIまたはイベント
3. タグ，データ，レシピ
4. Access Transformer等の限定的手段
5. Mixin
6. Reflection

Mixinは必要な感染生成・拡散処理だけに限定する．

広範なクラス置換やCDU内部の上書きは避ける．

Reflectionは原則使用しない．

## 13.3 互換層の分離

Spore固有処理を一般コードへ混在させない．

例:

```text
dev.upiscium.frontierprotocol
├── api/
│   └── suppression/
├── stabilization/
│   ├── block/
│   ├── blockentity/
│   ├── network/
│   └── registry/
├── spawnprotection/
├── integration/
│   ├── create/
│   └── spore/
│       ├── SporeCompat.java
│       ├── SporeSuppressionHooks.java
│       ├── SporeContentClassifier.java
│       └── mixin/
├── config/
└── test/
```

実際の既存構成に合わせて変更してよいが，依存方向は維持する．

```text
Spore互換層
    ↓
Frontier Protocolの公開抑制API

安定化装置
    ↓
抑制サービスへ範囲を登録

初期スポーン保護
    ↓
抑制サービスへ範囲を登録
```

安定化装置がSporeクラスを直接呼ぶ構成は避ける．

# 14. Createとの統合方針

Create統合では，可能な限り公開APIを利用する．

実装候補:

* KineticBlock
* KineticBlockEntity
* Stress impact
* Speed requirement
* Shaft接続
* Ponder
* Create加工レシピ
* Gogglesによる状態表示

# 23. READMEに記載する最終説明

READMEの概要は，次の趣旨に更新する．

> Frontier Protocol is a NeoForge addon for Fungal Infection: Spore and Create.
> It introduces Create-powered containment infrastructure that suppresses Spore infection across entire chunks, from the bottom to the top of the dimension. Players must build automated production lines and logistics networks to continuously supply and power containment devices, allowing sustainable settlements and industrial bases to exist inside an infected world.
>
> Frontier Protocol does not prevent hostile mobs from entering protected areas. Physical defense remains the player’s responsibility. Resource generation and infinite ore extraction are intentionally delegated to other Create addons.

日本語説明:

> Frontier Protocolは，Fungal Infection: SporeとCreateを統合するNeoForge向けアドオンMODです．Createの動力，生産設備および物流を利用して，チャンク全高にわたるSpore感染抑制設備を継続運転できるようにします．

# 25. 完成判定

Frontier Protocolの最小完成版は，次を満たした時点とする．

* SporeとCreateを必須依存として起動できる
* 初期スポーン5×5チャンクで感染生成・拡大が抑制される
* Mobは保護範囲へ侵入できる
* Tier 1装置をCreate回転力で稼働できる
* Tier 1装置が設置チャンク全高を抑制する
* 燃料または動力停止後，猶予期間を経て抑制が解除される
* 安定化セルをCreateで自動生産できる
* 既存感染が段階的に浄化される
* 巣は自動破壊されない
* サーバー再起動後に状態が維持される
* 専用サーバーで動作する
* チャンク全高の総当たり走査を行わない

Tier 2，Tier 3，詳細なPonder，TFMG統合および高度な表示は，最小完成版の後でもよい．
